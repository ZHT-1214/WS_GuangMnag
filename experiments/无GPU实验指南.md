# 没有机器人 / 没有 GPU 时，这篇论文的实验怎么做

**核心结论：你的系统本来就不需要机器人。**

WS_plus 是"Android 手机 + 云端服务"，不是机器人系统。`WS_plus/visualnav-transformer-扩散策略模型/` 里的 ROS 代码、Jetson 配置、蓝牙震动带是**早期遗留方案**，论文 §4.3 已把它作为"被替代的旧方案"来写，不参与当前实验。

所以真正缺的只有两样：**一台能跑推理的 GPU**、**一份按规范采集的数据**。

### 已跑出的三个真实发现（这是论文的加分项，不是减分项）

1. **方向判据有 14.3% 的"需确认"降级**：云端版比遗留边缘版更安全——旧版把"位移过小"误判为"向前"，新版如实报 unknown。
2. **拓扑图节点可区分性不足**：相邻节点相似度 0.982、远端 0.893，gap 只有 0.089；相邻最小值（0.9485）甚至低于远端最大值（0.9381），说明纯外观检索会误匹配，必须依赖 NoMaD 的距离预测头。
3. **窗口尺度失配**：节点中位间距 5.3 cm，radius=4 只覆盖 0.21 m，小于单步预测位移 0.425 m。

第 2、3 条是**在真实数据上发现的工程缺陷**，写进论文比编一个漂亮的成功率更有说服力，导师也能看出你真读了代码和数据。注意结论只依赖数据统计性质，与"谁采集的"无关——这正是可以放心引用的原因。

## 二、需要租 GPU 才能做的（1–2 天，几十元）

最低配置：**单卡 8 GB 显存即可**（NoMaD fp32 仅 72.67 MiB，YOSO-R50 约 200 MB）。按小时计费，跑完就关。

| 实验 | 脚本 | 需要什么 | 预计耗时 |
|---|---|---|---|
| E1 端到端时延 | `exp_latency.py` | 云端服务起来 + 手机连过去 | 半天 |
| E2 导航成功率 | `exp_navigation.py` | 按 §5.3 协议重新采集 3 条路线 | 1 天 |
| E3 避障干预/误报 | 同 E2 流程 + 人工摆障碍 | 同上 | 半天 |
| E4 仲裁器在线消融 | `exp_arbitration.py` | 真实 trace | 半天 |

**建议顺序**：先跑 E1（最快出数，证明系统真的能跑）→ 再重采数据跑 E2/E4 → 最后 E3。

## 三、必须重采数据的原因（重要）

现有 `tartan_drive` 数据是**前团队遗留的**（不是你的），而且采集时设备朝向没随行进方向转动：

- 航向变化中位数 0.04°，P99 仅 4.74°，最大 6.79°
- **超过 10° 的帧占比为 0**
- 图像分辨率也不一致：轨迹图 320×240，拓扑图 640×480（当前 App 是 640×480）

后果：轨迹几乎是直线，left/right/back 全为 0，**无法评估转弯识别**；且数据非你所采，学术上不能作为你的实验数据。

正确采法（论文 §5.3 已写明）：
1. 手机持于胸前，镜头正对行进方向；
2. 每步约 0.5 m 采一帧（当前是 1.2 s 一帧，会过密——这正是间距只有 5.3 cm 的原因）；
3. 转弯处放慢，保证覆盖 3–5 帧；
4. 每处场地采 3 次（不同光照/时段）。

采完用自己的数据重跑 `exp_offline_analysis.py` 与 `exp_navigation.py`，就能把论文里的"遗留数据分析"替换成"自采数据实验"——这是让论文从"有缺陷"变成"完整"的关键一步。
